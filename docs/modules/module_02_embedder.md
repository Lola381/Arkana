# Module 2 — Embedder

## Purpose
The Embedder module converts unstructured text chunks into 768-dimensional dense vectors and coordinates dual-storage persistence. It synchronizes writes to the Qdrant vector database (for semantic similarity search) and PostgreSQL (for BM25 sparse keyword search).

It serves strictly as a storage and search integration wrapper. It does not manage higher-level workflows, distributed transaction rollbacks, or document boundaries.

## Files
- `ai/ai/embedding/embedder.py`
- `ai/ai/embedding/test_embedder_fixes.py`

## Entry Points
- `Embedder.embed_chunks(chunks)`
- `Embedder.upsert_to_qdrant(chunks)`
- `Embedder.upsert_to_postgres(chunks)` (async)
- `Embedder.process_and_index(chunks)` (async)
- `Embedder.search_dense(query, filters, top_k)`
- `Embedder.search_sparse(query, top_k, tribe_name)` (async)

## Inputs
List of dictionary chunks generated by the Semantic Chunker (Module 1).
Schema:
```python
{
    "chunk_id": str(uuid4),
    "doc_id": str,
    "chunk_index": int,
    "text": str,
    "token_count": int,
    "tribe_name": str,
    "region": str,
    "time_period_start": str,
    "time_period_end": str,
    "institution": str,
    "source_title": str,
    "source_url": str
}
```

## Outputs
For `process_and_index`, returns a summary dictionary:
```python
{"embedded": int, "qdrant_upserted": int, "postgres_upserted": int}
```

For search methods, returns a ranked schema:
```python
[
    {
        "chunk": Dict[str, Any], # Raw chunk metadata + text
        "score": float,
        "rank": int
    }
]
```

## Current Architecture
The Embedder loads `sentence-transformers/all-mpnet-base-v2` synchronously at initialization. It pushes vector payloads via `qdrant_client` in HTTP/gRPC batches of 100, and uses `asyncpg` to upsert text/metadata payloads into a dynamically configured PostgreSQL table using `executemany` bindings. All orchestrating methods (`process_and_index`) and database IO functions (`upsert_to_postgres`, `search_sparse`) are fully asynchronous to prevent blocking the parent event loop.

## Final Implementation
1. `process_and_index()` receives a list of chunks and executes `embed_chunks()` synchronously (batched over CPU/GPU).
2. Tensors are converted to `numpy.ndarray` and appended to the chunk payload under the `vector` key.
3. The method triggers `upsert_to_qdrant()`, synchronously mapping the payloads to Qdrant `PointStruct` objects and flushing them.
4. The method then `await`s `upsert_to_postgres()`, which pushes the metadata and raw text (without the vector) into the `{postgres_table}` target via `asyncpg`.

## Implemented Improvements
### 1. Async Orchestration
- **Problem:** `process_and_index()` used `asyncio.run()` to trigger the async postgres upsert.
- **Root Cause:** A fatal synchronous wrapper was used to bridge a synchronous orchestration method to an async database client.
- **Implementation:** `process_and_index()` was converted to `async def` and `asyncio.run()` was replaced with `await`.
- **Impact:** The module can now be safely executed inside FastAPI or modern async ETL pipelines without triggering `RuntimeError: asyncio.run() cannot be called from a running event loop`.

### 2. Dynamic PostgreSQL Table Configuration & 3. Removal of Hardcoded SQL Table Names
- **Problem:** The module crashed with `psycopg2.errors.UndefinedTable: relation "chunks" does not exist`.
- **Root Cause:** The PostgreSQL table name `"chunks"` was permanently hardcoded into all `INSERT` and `SELECT` raw SQL strings, diverging from Arkana's actual target schema.
- **Implementation:** Added `postgres_table: str = "rag_chunks"` to `EmbeddingConfig` and injected it into all SQL string formatting.
- **Impact:** Safe targeting of target database schemas dynamically.

### 4. Pipeline Asynchronous Cascade
- **Problem:** Making `process_and_index()` async broke upstream components.
- **Root Cause:** The `chunk_and_index_documents` methods in `ArkanaPipeline` were synchronous.
- **Implementation:** The entire call stack in `ai/ai/pipeline.py` was refactored to `async def` and all internal invocations were upgraded to `await process_and_index()`. 
- **Impact:** Zero remaining synchronous callers. Complete async event loop compliance.

## Important Design Decisions
- **Embedder owns embedding + storage only:** The module is designed as a repository/adapter layer. It should not make business decisions about the data shape.
- **It should not own orchestration:** Decoupling enables the ETL module to handle scaling, multiprocessing, or event streaming safely outside of the vectorizer.
- **It should not own transactions:** If PostgreSQL fails, Qdrant vectors will be orphaned. Implementing two-phase distributed commits or outbox patterns belongs strictly to a dedicated orchestration layer (Indexing Bridge), not this repository class.

## Assumptions
- `chunk_id` values perfectly map to valid standard UUIDs.
- PostgreSQL full-text search relies on the `english` configuration (`to_tsvector('english')`).

## Known Limitations
- The underlying `embed_chunks` encoding function remains CPU/GPU synchronous and blocking.

## Integration Points
- **Upstream:** Invoked by the Indexing Bridge (`pipeline.py`).
- **Downstream:** `search_dense()` and `search_sparse()` are relied upon strictly by the Retriever (Module 3).

## Breaking Changes
- **API Migration:** Any existing legacy callers to `process_and_index` had to migrate to `async/await`.
- **Data Persistence:** Module 2 logic changes (async cascade and dynamic tables) DO NOT independently require PostgreSQL/Qdrant to be rebuilt. However, **a complete rebuild is already planned and mandatory because Module 1 changed the fundamental chunk boundaries and overlap mechanics.**

## Future Improvements
* **Two-phase commit / rollback**
  * **Why deferred:** Cross-database consistency (e.g. handling orphaned Qdrant vectors on Postgres timeout) belongs to orchestration.
  * **Future owner:** Indexing Bridge
  * **Expected module:** Module 10 (ETL / Indexing Bridge)

## AI Notes
- **Safe refactors:** Connection pooling logic, Qdrant client connection parameters, and embedding batch sizes.
- **Things that must never change:** `model_name` (`all-mpnet-base-v2`), `vector_size` (768), and Qdrant distance function (`Distance.COSINE`). Any alteration corrupts the underlying mathematical space.
- **Public interfaces:** The search dictionary schemas (`chunk`, `score`, `rank`) returned by sparse and dense search must not be altered, as HybridRetriever tightly couples to them.
- **Configuration assumptions:** `qdrant_url` defaults to `http://localhost:6333`.
- **Dependencies:** `sentence-transformers`, `qdrant-client`, `asyncpg`.
